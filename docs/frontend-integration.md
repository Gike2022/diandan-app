# React 顾客前端接入说明

现有粉紫色主题、星空背景、分类侧栏、菜品卡片和购物车布局保持原有风格；数据通过 Express API 保存到 MySQL。

## 本机运行

在项目根目录打开两个终端：

```powershell
# 终端一：已配置本机 MySQL，无需重新输入连接密码
npm run dev:api
```

```powershell
# 终端二
npm run dev
```

打开 <http://127.0.0.1:5173>。本机演示顾客账号为 `demo`，密码为 `Customer12345!`；管理员演示账号为 `admin`，密码为 `Admin12345!`。这些是网站演示账号，与数据库连接密码无关。新环境先按照 [后端说明](../server/README.md) 配置、迁移并初始化数据库。

## 演示流程

1. 匿名浏览菜单并加菜，进入购物车。首页的历史订单和登录入口位于右上角。
2. 点击结算；未登录时进入登录页，登录成功自动回到结算页面。
   没有账号时点击“注册账号”，输入账号、昵称、可选联系电话和两次密码；注册成功自动登录并回到结算，购物车保持原内容。注册账号为顾客，不能注册管理员。
3. 填写联系人、手机号、地址和可选备注，选择微信或支付宝模拟方式，确认下单。
4. 详情页显示后端核算的最终金额。点击“模拟付款失败”可演示重试，点击“模拟付款成功”后订单进入待接单状态。
   默认需在 15 分钟内付款，详情显示剩余时间；到期后自动取消并显示原因，不能继续付款。后台任务不依赖页面打开，服务重启也会补扫到期订单。
5. 查看历史订单，可继续付款、查看详情、取消未付款订单或再来一单。商家通过现有管理 API 修改状态后，活动订单每 5 秒刷新。
6. 退出后个人查询缓存清空。登录其他账号时只能查看该账号自己的订单。

包装费为每份菜品 0.50 元；结算金额由后端根据数据库价格计算。模拟支付不展示真实收款码，也不会产生真实扣款。商家管理页面现已接入，见 [商家指南](merchant-guide.md)。

## 配置与数据恢复

默认前端请求 `/api`，Vite 将其转发到 `http://127.0.0.1:3001`。需要修改时可从根目录 `.env.example` 创建 `.env`，已有配置文件请保留原值：

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

`API_PROXY_TARGET` 控制本地代理，`VITE_API_BASE_URL` 控制浏览器请求地址；修改后重启 Vite。后端连接密码仅放在 `server/.env`，不得放入 `VITE_*` 变量。独立部署还需配置后端允许的前端来源，见 [部署说明](../部署说明.md)。

购物车保存在 localStorage，刷新后恢复。新格式使用 `sweet_kitchen_cart_v2` 的 revision、菜品和消费标记，自动迁移原有 v1 购物车。同来源的标签页通过 storage 事件同步，在支持 Web Locks 的浏览器中串行修改快照，结算时重新读取当前快照。登录令牌也保存在浏览器本地，刷新时重新验证；退出会清理令牌和购物车，服务端会撤销会话。历史订单始终从数据库读取，旧版 localStorage 的模拟订单不会作为真实订单展示。

下单前将本次请求及幂等键保存到当前标签页的 sessionStorage。若服务端已创建订单但响应丢失，刷新后点击“重试确认订单”会使用相同请求确认原订单，避免重复下单。只有确认成功后才从购物车扣除本次购买的数量。再来一单重新读取当前菜单，更新共享菜单缓存，使用当前价格和菜品 ID；停售、售罄时提示重新选择。

新订单幂等键由共享购物车 revision 派生，避免两个标签页为同一购物车生成不同键。成功后在同一次本地写入中保存扣除结果和消费标记，重复确认不会再次扣掉请求期间新加的菜。同一购物车提交不同收货信息时由后端拒绝内容冲突，顾客可到历史订单核对；明确重新加菜或再来一单会生成新购物车 revision，允许创建下一笔订单。

## 自动化验证

```powershell
npm run typecheck
npm run typecheck:api
npm run build
npm run build:api
npx playwright install chromium
npm run test:e2e
npm run test:api
```

浏览器测试自动启动独立 API（3002）和 Vite（5174），使用真实 MySQL 的 `TEST_DATABASE_URL`。启动时清理该测试库的点餐业务记录并初始化演示数据；脚本要求测试库名称以 `_test` 或 `_test_十六进制后缀` 结尾，并与应用库不同。不会清理应用库。浏览器与 API 集成测试使用同一测试库，需顺序执行。

顾客 10 项浏览器测试覆盖动态菜单、登录错误与返回、购物车刷新、下单和手机号保存、微信/支付宝模拟方式、失败重试、成功后刷新、响应丢失后的重复确认、历史查询与继续付款、状态更新、取消、最新价格再来一单、账号隔离、会话失效、接口失败与空菜单，以及窄屏/横屏无横向溢出。另有 9 项商家测试，覆盖权限、菜品分类管理、接单到完成、拒单退款和异常恢复，见商家指南。测试中的外部菜品图片使用占位图，上传测试读取实际生成文件，避免外部图片服务波动影响业务验证。

`e2e/flow-regressions.spec.ts` 另含 5 项缺陷回归：新增响应丢失后刷新重试、旧表单版本冲突、双标签同步及并发结算（包括请求期间加菜）、接单后分页退回、UTC 更新时间。后端也验证并发管理创建幂等、版本竞争和连接池全部会话 UTC。

注册与超时功能增加 `e2e/registration-expiry.spec.ts` 的 3 项流程，覆盖注册密码/重名反馈、自动登录返回与首单、倒计时到期及历史原因、无人打开页面时后台取消、已付款不误取消、锁等待跨截止时间、扫描竞争与重启补扫。

`e2e/merchant-search-alerts.spec.ts` 增加 4 项商家查询与提醒流程，覆盖订单号/日期/状态组合、筛选返回第一页、无结果/日期错误恢复、条件生效与重置、付款提醒、切页刷新去重、断网补查、同数量换单和批量合并。新查询接口和提醒快照见 [接口说明](backend-api.md)，使用方式见 [商家指南](merchant-guide.md)。

`e2e/statistics-images-account.spec.ts` 增加 7 项统计、上传和账户流程；当前共 38 项浏览器测试、40 项真实 MySQL API 测试。覆盖日期/指标与明细、空统计和失败恢复、图片上传失败/预览/保存/顾客展示、资料更新/清空电话/刷新及结算默认值、改密验证/新旧密码登录/会话撤销，以及商家资料入口和手机桌面截图。见 [扩展功能操作说明](statistics-images-account-guide.md)。

浏览器测试服务使用更高的测试登录限额和 100 毫秒扫描周期，以支持完整套件多次登录及快速验证；正常 API 默认仍为每来源 15 分钟 30 次认证请求、30 秒扫描周期。测试仅在独立库调整目标订单截止时间，不在应用库加速到期。
